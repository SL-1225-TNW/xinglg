## 审查结论

出口固定在底部中央，是房间生成器的约定，不是切换场景引擎的限制。`checkExit()`（game.js:2043）逐项匹配 `map.exits`，已有多出口能力；`doSwitchScene()` 接受任意目标坐标。

| 问题 | 代码位置 | 影响 |
| --- | --- | --- |
| 城市室内只在底部中央开一格出口 | game.js:3013–3016 | 所有建筑沿用同一个出口布局 |
| 磨坊、牧场与扩展房间也采用中央出口 | game.js:14486–14491、14846–14849 | 新地区继承相同限制 |
| 进入城市、乡村、扩展室内时重新计算中央落点 | game.js:11893–11895、15103 | 只改出口，进门仍会出现在旧位置 |
| 城市室内缓存连续绘制四面墙边，没有根据出口画门洞 | game.js:5364–5384 | 可走出口与可见门的形状没有绑定 |
| 农舍门的外观单独读取硬编码门格 | game.js:1827、13278 | 只改 exits，门的图像不会一起移动 |
| 通用出口箭头按横坐标判断左右 | game.js:12714–12724 | 上下出口的方向提示可能错误 |
| 委托出口引导写死农舍坐标，其他室内没有通用回退 | game.js:7654–7660 | 门位置变化后可能继续指向旧出口 |

注意：`millroom`、`vetroom` 等旧场景已由 game.js:15579 后的兼容代码合并到正式场景。实施应优先覆盖 `mill_workshop`、`meadow_vet` 等正式场景，兼容入口继续接入正式场景。

## 门的共同配置

为室内增加 `doors`，每扇门保存：唯一 ID、所在墙面 north/south/east/west、门格及宽度、名称、外观样式、室内安全落点、目标场景及目标安全落点。多格宽门仍是一扇门，不能生成多个重复交互提示。

门的位置、门洞碰撞、画面、出口和进入落点都从同一配置派生。保留现有 `map.exits`，由门配置生成对应出口格，继续复用 `checkExit()`。室外入口关联目标门 ID，统一入口函数读取该门的室内落点；淘汰各入口里独立计算中央坐标的代码。

生成顺序：墙与地板 → 家具 → 检查门洞及通道冲突 → 安装门洞与出口。发生家具冲突应调整布局并报出配置问题，不能仅清除 solid，否则会留下“家具还画着但能穿过去”的现象。只为墙上的出口开洞，其他墙面保留碰撞。

## 玩家体验

- 门应看得出来：门框、门洞或门板、门槛、门前小地垫；按墙面方向绘制。城堡用双扇门，厂房可用宽装卸门，小屋用木门。
- 默认继续走到门槛自动出门；在门旁增加“出口 · 返回某地”的提示。可同时支持 E 和手机交互键，二者调用同一个切换函数，提示明确说明可以走过去出门。
- 进门落在对应门内侧，出门落在对应室外门前；落点不设在自动切换格上，避免进出反复触发。必要时增加短暂防重入保护。
- 门支持四面墙、偏左偏右和多扇门，但每扇额外出口都必须对应真实可达的室外入口与落点。第一轮不为了多门而给所有房间随意新增后门。
- 委托引导从真实出口数据选择可达且适合目标路线的门；出口箭头使用门方向。无法确定目标路线时才回退到可达的默认门。

## 实施顺序

1. 建立门配置、安装函数、统一进门函数和门绘制函数，接入现有 exits。先保持现有位置，让所有正式室内有明确可见的门。
2. 迁移农舍、城市房间、磨坊与牧场、扩展地区房间的入口和出口；同步修改提示、箭头、委托引导。城市房间门纳入 `_roomCanvas`，门配置变化时失效缓存；普通房间同步失效地面分块缓存。
3. 选小屋、城市大厅、宽厂房各做一个试点：偏置单门、双格宽门、侧门。确认四种方向都支持后，再按房间功能调整其他建筑。新增室外侧门时一起核对建筑碰撞、入口交互和外观。
4. 补充有意义的验收并重建单文件版。门属于静态地图配置，初版不需要新增存档字段；加载旧存档时仍需检查当前位置，避免新墙或家具把玩家困住。

## 验收要求

- 遍历正式室内：每扇门的可见位置、出口格和配置一致；进门落点至门槛存在可走路径。
- 上、下、左、右门以及两格宽门均可正常通行；非门墙面无法穿越。
- 多门房间从不同入口进入，各自对应正确室内落点，返回正确室外门前。
- 门附近没有家具堵路、墙线遮住门洞或自动往返切换。
- 真实键盘移动及手机移动/交互可进出，委托提示指向有效出口。
- 老存档、场景合并兼容入口、室内天气回归正常；开发页与重建后的单文件版行为一致。

建议首轮目标：所有正式室内有可辨识的门，门可配置在任意墙面，进出落点与门同步。随后依据建筑用途逐栋配置侧门和后门。
